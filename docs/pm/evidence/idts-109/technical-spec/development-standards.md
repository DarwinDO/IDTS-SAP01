# Development Standards — Candidate

| ID | SAP/classic concept | CAP/Fiori equivalent used by IDTS | Project rule | Scope | Verification/evidence |
| --- | --- | --- | --- | --- | --- |
| STD-01 | Development object naming | CDS namespaces, services, entities, actions and JavaScript modules | Use business-readable English names; entity names are plural, actions are verbs, codes are stable uppercase values, and generated/runtime names are not copied into business wording. | `db/`, `srv/`, `app/` | CAP compile; review `db/schema.cds` and `srv/service.cds` |
| STD-02 | ABAP package/layer separation | CAP `db`, `srv`, `app` layers | Persisted model, service contract/logic and UI concerns remain separated. UI code must not become the source of business authorization. | Whole solution | Repository structure and CAP compile |
| STD-03 | Data Dictionary/domain checks | CDS types, associations, code-list entities and active flags | Validate required fields, types, active catalog values and cross-catalog relationships before commit. | Bug write and AI apply | `qa:idts41:programmatic`, `qa:idts93:programmatic` |
| STD-04 | Transaction unit of work | CAP request transaction through `cds.tx(req)` | Business mutation, history and in-app notification that belong to one action commit together or roll back together. External email is processed after commit. | Bug lifecycle, history, notification | Programmatic lifecycle/history and email-outbox tests |
| STD-05 | Authority check / authorization object | CAP roles, request user and handler authorization | Enforce role and ownership in backend handlers. UI visibility is guidance, not authorization. | All protected reads/actions | Auth tests and negative role tests |
| STD-06 | Message class | Stable catalog IDs mapped to exact source messages | Reuse stable IDs in the specification; do not invent messages or expose stack/provider details. Every catalog row records trigger, status, target, rollback, logging, UI handling and evidence. | Backend, UI, worker, provider | `message-catalog.md`; source scan |
| STD-07 | Exception class and error mapping | `req.reject`, safe provider results and controlled UI error mapping | Use 400 for invalid input/state, 401 for missing/invalid session, 403 for authorization, 404 for missing business objects, 409 for stale/conflicting state, and generic safe text for unexpected failures. | CAP services and UI | Negative tests; auth and AI tests |
| STD-08 | Dynpro/Fiori screen behavior | Fiori Elements annotations plus supported SAPUI5 extension controls | Prefer annotations and stable extension points. Do not modify generated Fiori Elements DOM. Use MessageStrip for persistent context, MessageBox for blocking failures/confirmation and MessageToast for brief success/status feedback. | Fiori/UI5 | UI5 build/lint; browser evidence |
| STD-09 | OData service design | CAP OData V4 projections, bound/unbound actions and functions | Use entity reads for queryable data, actions for mutations or request-style AI operations, and a function for read-only AI metrics. Keep service contracts explicit in `service.cds`. | `srv/service.cds` | CAP compile and contract tests |
| STD-10 | Draft handling | CAP draft lifecycle for Bug create/edit | Validate draft input and active data consistently; side effects belong to successful activation/save, not an abandoned draft. | Bug create/edit | Draft and code-list QA |
| STD-11 | Audit/change documents | `HistoryEvents`, `HistoryLogs`, `AiSuggestions` review metadata | Record actor, time and meaningful business change. Do not use UI labels as the audit source of truth. | Bug lifecycle and AI review/apply | History and IDTS-91/93/95 tests |
| STD-12 | Background processing | Durable notification outbox and bounded worker | Provider delivery is decoupled from the bug transaction; use delivery state, retry/lock controls and sanitized summaries. | Email notification | `qa:email-outbox:programmatic` |
| STD-13 | External provider boundary | S3/email/OpenAI adapters behind validated configuration | Read credentials only from private runtime configuration; never persist or document secrets. Provider failures must not corrupt the core bug workflow. | Attachments, email, AI | Secret scan; provider failure tests |
| STD-14 | AI human control | Persisted suggestions plus separate review/apply/confirm actions | AI never autonomously assigns, reclassifies, confirms a duplicate or changes workflow status. Accept/Reject/Ignore records a review decision; apply/confirm is explicit and allowlisted. | AI features | IDTS-91, IDTS-93, IDTS-95 QA |
| STD-15 | AI privacy and safety | Input allow-list, redaction, timeouts and sanitized audit | Limit input size, remove sensitive text, avoid raw prompt/response/error persistence and expose only safe provider/model aliases and metrics. | `srv/ai/` | `qa:idts71:programmatic`, secret scan |
| STD-16 | Localization | English i18n resource and stable technical identifiers | Submission and user-facing production wording are English. Technical IDs remain unchanged. New reusable UI messages should use i18n rather than duplicated literals. | SAP490 artifact and UI | i18n review and UI5 lint |
| STD-17 | Test naming and traceability | Jira-keyed QA scripts and evidence folders | Tests must cover positive, negative, boundary, authorization, persistence/reload and UI behavior when applicable; evidence must point to a reproducible command or sanitized artifact. | `scripts/qa/`, `docs/pm/evidence/` | `package.json` QA scripts; evidence review |
| STD-18 | Source control/change control | Task branch, focused diff, review and final integration owner | Keep candidate source separate from the official artifact, preserve unrelated work and require member approval before DonHV integrates the final workbook. | IDTS-109 | Branch/diff review, Jira approval comment |
| STD-19 | Logging | CAP category logs with sanitized context | Log stable action/error categories and correlation data only; exclude passwords, bearer tokens, private URLs, raw provider payloads and full private email lists. | Backend and workers | Secret scan and source review |
| STD-20 | Configuration portability | CAP configuration with safe defaults | Do not hardcode deployment endpoints or credentials. Local SQLite is development-only; persistence/provider targets remain configurable. | Deployment-facing code | Configuration review and secret scan |
