# Knowledge: `srv/notification/scheduled.js`

## English

This module is the N4 technical scheduler boundary for Pending Assignment SLA and Overdue discovery. `processNotificationSchedules(req)` accepts only the CAP `OutboxProcessor` scope and ignores arbitrary client filters; the server supplies the current timestamp when the action does not provide one. `discoverScheduledNotifications({ tx, now })` reads only open Pending Assignment or past-due Bugs in bounded pages of 500, resolves active PM recipients for assignment/SLA events, and resolves active current-action owners plus distinct technical assignees for Overdue events. Each keyset page runs through a detached CAP root transaction derived from the supplied database/transaction service, carrying the request tenant and user when `tx` came from `cds.tx(req)`; the public `{ tx, now }` interface remains unchanged.

The existing `writeNotificationRecord()` is the single transactional producer for Bug discovery. It inserts one source-keyed `Notifications` event, one personal inbox index row, and—only for Critical/Blocker Pending Assignment or SLA—one prompt email outbox row. Normal SLA reminders and all Overdue events are inbox/digest policy only. Keys `PENDING_ASSIGNMENT:<bugID>:<recipientID>`, `SLA:<bugID>:<threshold>h:<recipientID>`, and `OVERDUE:<bugID>:<dueDate>:<dueDateHistoryEventID>:<recipientID>` make schedule repeats no-ops; the immutable due-date history-event identity makes every changed-date cycle new, including when a prior date is reused. The module never sends email or calls the existing `processEmailOutbox` worker. During the Bangkok-local weekday 08:00–08:59 recovery hour, `processNotificationSchedules(req)` also invokes `scheduleNotificationDigests()` in a fresh detached CAP root; digest creation still only stores a snapshot, while the existing worker owns delivery.

Pending Assignment SLA age uses the latest immutable `HistoryLogs.createdAt` for a status change into `PENDING_ASSIGNMENT`, falling back to immutable Bug `createdAt` for legacy rows without that audit. It never uses mutable Bug `modifiedAt`. Critical/Blocker is due at four hours and other priorities/severities at 24 hours. Overdue compares the date-only due date to the fixed run date and excludes `CLOSED` Bugs. A page CAP root transaction preloads profile-to-user pairs, locks relevant recipient Users once per bounded page, then locks candidate DeveloperProfiles before locking any Bug rows, matching the safe `User -> DeveloperProfile -> Bug` order (and the assignment/deactivation `DeveloperProfile -> Bug` suffix). It then locks and re-reads each candidate Bug before deriving eligibility, and performs one final page-bounded active-profile/User read after Bug revalidation; a profile that was deactivated after preload cannot remain an eligible technical recipient. Final recipient Users are still locked/revalidated before the writer. Assignment/closure/due-date/profile changes therefore cannot produce stale events or unbounded query amplification. CAP commits the page after all its source/inbox/delivery writes, releasing every page lock before keyset continuation starts; a failure rolls back that page's complete source/inbox/delivery unit. This detached page scope is necessary because a request `cds.tx(req)` is nested and holds `forUpdate()` locks until its root commit; the scheduler has no caller business writes to combine with these maintenance pages, so it carries tenant/user context into each root transaction instead of silently committing a caller transaction.

Candidate pages use keyset continuation (`ID > lastID`) rather than OFFSET, so concurrent rows moving in or out of the candidate set cannot shift later pages. Overdue keys retain the due-date value and add the immutable due-date `HistoryEvents` identity; changing `2026-08-26` to `2026-08-25` and back therefore creates a new cycle even when a prior date is reused.

## Tiếng Việt

Module này là boundary scheduler kỹ thuật của N4 để discovery SLA Pending Assignment và Overdue. `processNotificationSchedules(req)` chỉ nhận scope CAP `OutboxProcessor` và bỏ qua filter tùy ý từ client; nếu action không truyền timestamp thì server dùng thời điểm hiện tại. `discoverScheduledNotifications({ tx, now })` chỉ đọc Bug đang Pending Assignment hoặc đã quá due date theo page bounded 500, resolve PM active cho event assignment/SLA, và resolve current action owner active cùng technical assignee khác người cho event Overdue. Mỗi page keyset chạy qua một CAP root transaction detached được derive từ database/transaction service truyền vào, giữ tenant và user của request khi `tx` đến từ `cds.tx(req)`; interface công khai `{ tx, now }` không đổi.

Module dùng `writeNotificationRecord()` hiện có làm producer transactional duy nhất. Hàm này insert một event `Notifications` có source key, một row inbox cá nhân và—chỉ với Pending Assignment hoặc SLA Critical/Blocker—một row email outbox prompt. SLA mức thường và mọi Overdue chỉ theo policy inbox/digest. Các key `PENDING_ASSIGNMENT:<bugID>:<recipientID>`, `SLA:<bugID>:<threshold>h:<recipientID>` và `OVERDUE:<bugID>:<dueDate>:<dueDateHistoryEventID>:<recipientID>` khiến schedule chạy lại thành no-op; identity HistoryEvent bất biến làm mỗi cycle đổi due date thành key mới, kể cả khi quay lại ngày cũ. Module không gửi email và không gọi worker `processEmailOutbox` hiện có. Trong hour recovery 08:00–08:59 ngày thường Bangkok, `processNotificationSchedules(req)` cũng gọi `scheduleNotificationDigests()` trong root detached riêng; generation chỉ lưu snapshot, worker hiện có mới delivery.

Tuổi SLA Pending Assignment dùng `HistoryLogs.createdAt` bất biến mới nhất của lần đổi status sang `PENDING_ASSIGNMENT`, fallback về `createdAt` bất biến của Bug legacy không có audit. Module không dùng `modifiedAt` mutable. Critical/Blocker đến hạn sau bốn giờ, priority/severity khác sau 24 giờ. Overdue so sánh due date chỉ lấy phần ngày với ngày chạy cố định và loại `CLOSED`. Mỗi root transaction CAP của page preload cặp profile-user, lock User recipient liên quan một lần bounded theo page, rồi lock DeveloperProfile trước mọi Bug, giữ thứ tự an toàn `User -> DeveloperProfile -> Bug` (và suffix assignment/deactivation `DeveloperProfile -> Bug`). Sau đó lock và đọc lại từng Bug trước khi derive eligibility, rồi đọc lại profile/User active một lần bounded theo page sau Bug revalidation; profile đã bị deactivate sau preload không còn là technical recipient hợp lệ. User recipient cuối vẫn lock/revalidate ngay trước writer. Vì vậy thay đổi assignment/đóng/due date/profile không tạo event stale hoặc query amplification. CAP commit page sau khi ghi xong source/inbox/delivery, nhả toàn bộ lock trước khi tiếp tục keyset; lỗi sẽ rollback trọn unit source/inbox/delivery của page đó. Scope detached này cần thiết vì `cds.tx(req)` của request là nested và giữ lock `forUpdate()` đến root commit; scheduler không có business write của caller để gộp nên truyền tenant/user vào từng root transaction thay vì âm thầm commit transaction caller.

Page candidate dùng keyset tiếp nối (`ID > lastID`) thay vì OFFSET, nên row đồng thời vào/ra tập candidate không làm lệch page sau. Key Overdue giữ due-date và thêm identity `HistoryEvents` bất biến của lần đổi due date; đổi `2026-08-26` sang `2026-08-25` rồi quay lại vẫn tạo cycle mới dù ngày cũ được dùng lại.

## Safe editing / Sửa an toàn

Keep the module source-only and scheduler-only: do not add a new worker/provider, broaden the candidate predicate, email normal reminders/Overdue, expose raw recipient/provider fields, merge discovery into `processEmailOutbox`, or reuse a caller-owned CAP root transaction across keyset pages. Keep each page's source/inbox/delivery writes in its own detached root and carry only the caller tenant/user context. Digest generation is a stored-snapshot handoff; it must not send mail or rebuild a row during retry. / Giữ module chỉ source và scheduler: không thêm worker/provider mới, mở rộng predicate candidate, gửi email reminder thường/Overdue, expose field recipient/provider thô, gộp discovery vào `processEmailOutbox`, hoặc dùng lại caller-owned CAP root transaction qua nhiều page keyset. Giữ write source/inbox/delivery của từng page trong root detached riêng và chỉ truyền tenant/user context của caller. Generation digest chỉ bàn giao snapshot đã lưu; không được gửi mail hoặc dựng lại row khi retry.
